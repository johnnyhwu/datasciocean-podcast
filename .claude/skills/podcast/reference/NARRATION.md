# 敘事工法 —— 怎麼寫給「只能用聽的」聽眾

這一層處理內容與結構,不處理 TTS 參數(那在 GEMINI-TTS.md)。

## 唯一的前提

**聽眾看不到任何東西。** 沒有圖、沒有表、沒有程式碼、不能倒帶重看,
而且多半是第一次接觸這個題目,可能還一邊在通勤或洗碗。

所有規則都是從這一句推導出來的。

---

## 一、開場三件事,缺一不可

| beat | role | 作用 |
|---|---|---|
| hook | `hook` | 丟一個具體的謎題,**不要劇透答案** |
| 節目識別 + AI 揭露 | `identity` | 說明聲音是 AI 合成 |
| **你會學到什麼** | `promise` | 明講聽完會拿到哪 2-3 樣東西 |
| **路線圖** | `signpost` | 這集會走幾站、每站講什麼 |

`promise` 和路線圖是給「要不要投資 30 分鐘」這個決定用的。
路線圖還要順帶講一句:「中間我會不斷停下來幫你收攏,
就算某一段沒跟上,下一個路口都可以重新上車」—— 這句話本身就降低了棄聽率。

## 二、每個專有名詞獨立一段,而且要有比喻

這是聽覺版本跟文字版本差最多的地方。文字可以讓讀者回頭看,聲音不行。

實際用過、效果好的比喻:

| 名詞 | 比喻 |
|---|---|
| context window | 模型的**工作桌面** —— 桌子多大就只能攤多少東西 |
| self-attention | **會議室交換眼神** —— 十個人九十次,一百個人九千九百次 |
| embedding | 幫每句話**標一個座標** —— 意思接近的座標就靠在一起 |
| benchmark | **學測考卷** —— 大家考同一份,分數才能比 |
| p95 | 最慢的那 5% —— 使用者記得的是最痛苦的幾次,不是平均 |

比喻要在名詞第一次出現時就給,不要等。

## 三、結構性約束

不要在 prompt 裡寫「請講得生動一點」,而是讓 schema 逼出變化。`pipeline/validate.py`
強制檢查:連續解說段的上限(中間必須插 `signpost`、`recap` 或 `turn`)、
`recap` 與 `signpost` 的下限、短 beat 的數量與長度變異、語氣提示的種類。
**門檻以 `validate.py` 為準**,這裡不重複列數字。

## 四、recap 的寫法

**列點,不要複述。** 而且**用問句收尾**,把聽眾推進下一段:

> 「到這邊先收一下。我們現在知道兩件事:第一,…;第二,…。
>  所以真正的問題就變成——如果不能全部記住,那要記什麼?什麼時候該忘掉?」

最後那個問句同時是下一段的路標。這是最省成本的開放迴圈。

## 五、埋預期,然後打破它

單人節目沒有雙主持人的天然落差,得靠**立場切換**製造。
最有效的手法是先讓聽眾相信一件事,隔一段距離再推翻:

- `b35_expect`:「照理說 graph 版應該在 multi hop 大幅領先。請記住這個預期。」
- `b47_payoff`(隔了 12 段):「結果它恰恰輸在 multi hop。」

距離要夠遠,落差才有力。

## 六、立場保真

論文沒說的話,要明講是自己的推論:

> 「論文沒解釋,那我講一下我自己的猜測,**先聲明這是我的推測不是論文的說法**。」

這一條使用者特別點名喜歡。它同時是誠實,也是可信度。
**自己的推測可以講,前提是每一次都明說「這是我自己的推測」。**

反過來,**部落格原文自己的矛盾不要講**(數字前後不一致、圖說跟圖對不上、
結論跟表格對不上):我們沒有論文全文,不替原文裁決,稿裡直接略過那一點,
並在交付總結裡列出。原文作者的批評與質疑不在此限,照常講。

## 七、人性化的口語

保留這類句子,它們讓整集不像唸稿:

- 「欸,這邊我想停一下」
- 「你可能會想,那不是…就好了嗎?」
- 「這裡有個細節值得注意」

## 八、⚠️ 插入路標之後,一定要修剪下一段的開頭

**這是實際踩過的坑。** 先寫完內文、事後插入 signpost,結果路標把內文的
第一句又講了一遍,聽起來像跳針。而 STT 驗證完全抓不到 ——
兩段各自都唸得正確。

ep001 有四處:

| 路標 | 下一段開頭 |
|---|---|
| 「那選項有哪些?只有四個,**我一個一個講**」 | 「而選項只有四個,**我一個一個講**」 |
| 「第三個稍微技術一點,但**我拆開講**」 | 「第三個理由比較技術性,**我拆開講**」 |
| 「那比**字面會有什麼問題**?」 | 「**字面重疊有什麼問題**?」 |
| 「接下來是這套設計**真正難的地方**」 | 「這裡才是**真正麻煩的地方**」 |

`validate.py` 會抓**字面重複**(≥8 字且含 ≥4 個中文字),
但上表後三組是**換句話說的重複**,程式抓不到 ——
所以插完路標一定要自己把相鄰兩段連起來讀一次。

## 九、停頓

停頓由 `stitch.py` 的 `gap_for` 依 role 自動處理,數字以程式為準。
寫稿時只需要知道一件事:`signpost` 的停頓最短,路標要接得緊,停久了反而斷。

---

## 十、英文版:重寫,不是翻譯

同一集要出英文版時,**骨架沿用、內容重寫**:

| 欄位 | 做法 |
|---|---|
| `id` / `role` / `beat` | **一對一沿用中文版**,兩版才對得起來、日後改稿好追 |
| `text` | **重寫。**逐句翻譯會壞掉,原因見下 |
| `style` | 換成英文骨幹句 + 對應語氣(語氣描述要一句一句對齊中文版) |
| `voice` | **不用改。**Gemini 的 prebuilt voice 與語言無關,同一個 `Zubenelgenubi` 講英文是同一把嗓子 |

### 為什麼不能直接翻

1. **中英夾雜的定錨消失了。** 中文版靠「knowledge graph」「Agent」用英文唸出來,
   讓聽眾一耳認出「這是術語」。英文版全是英文,這個訊號沒了 ——
   術語第一次出現時得改用**停頓 + 當場解釋**來標記。
2. **中文詞義解釋要整段刪掉。** 「context window,中文常翻成上下文視窗」
   對英文聽眾是雜訊。
3. **類比是文化性的。**

   | 中文版 | 英文版 |
   |---|---|
   | 小明住台北 / 台北在台灣北部 | Alice lives in San Francisco / San Francisco is in northern California |
   | benchmark 像**學測考卷** | like a **standardized test** |

   Alice / San Francisco 這組還有額外好處:論文原文 `b29` 用的就是它,兩邊自然接上。

### 門檻換算

英文的字元密度約為中文的 **2.8 倍**(一個音節平均 3 個字母以上),
所以所有以字元計的門檻都要換一套。`validate.py` 與 `verify.py`
會**自動判斷語言**(中文字佔比 > 15% 算中文),不需要下參數:

| | 中文 | 英文 |
|---|---|---|
| 正常語速 | 4.0-9.5 字/秒 | 11.0-20.0 字元/秒 |
| 失控下限 | 3.5 | 9.0 |
| 每分鐘字元 | 260-330 | 760-950 |
| 短 beat | < 60 字元 | < 170 字元 |
| 長度標準差下限 | 40 | 110 |
| 相鄰段重複判定 | 8 個字元 | 5 個**詞** |

最後一列是重點:英文用字元數當門檻會把 `the memory` 這種碎片也算成重複,
所以英文改成比詞序列。

### 正規化差異

`NORMALIZATION.md` 的規則多數照舊 —— `48.7%`、`GPT-4o-mini`、`LLM` 一樣直接寫。
三點要注意:

- **`Mem0` → `Mem zero` 仍然要改。** 英文聽眾同樣會聽成 memo。
  (`verify.py` 會把兩邊都折回 `Mem0` 再比,所以不會因此扣分。)
- **`arXiv` 直接寫。** Whisper 會轉錄成 "Archive",那是**正確發音**,不是唸錯。
- **數字直接用英文寫,不要為了分數改成阿拉伯數字。** Whisper 一律寫數字
  (`9,900`、`600`、`26,000`、`24%`、`95th`),稿子寫詞才唸得對。
  `verify.py` 兩邊都會折算,ep001 英文版靠這條從 0.969 拉到 0.999。

### 成本

中英兩版的音訊長度本來就差不多(都是 28-40 分鐘),而成本由輸出音訊長度決定,
所以兩版都是 **US$1-1.5/集** 量級,不是「英文貴三倍」。細節見 `GEMINI-TTS.md`。
