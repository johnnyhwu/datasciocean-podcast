## 30 秒版本

把每篇部落格文章自動轉成一集 15-20 分鐘的單人口白 podcast,上架 Apple Podcasts 與 Spotify。

**流程**:文章 → LLM 抽取成結構化 beats → LLM 渲染成逐字稿 → 本地 TTS 合成 → 程式化拼接與音量正規化 → 手動上傳。

**四個決定性的設計選擇**:

1. **中間插一層 beats(結構化 JSON),不讓 LLM 一步從文章生成逐字稿。** 這一層同時解決四件事:未來擴充雙人對談時不必重新分析文章、**英文版只需多一個渲染分支**、品質檢查成本大幅降低、長度控制變成可計算而非靠 LLM 猜。
2. **文章是唯一真理來源(single source of truth)。** 不只禁止幻覺,連「正確但文章沒寫」的補充也一律擋下。所有音訊內容都必須能溯源回文章的某一段。
3. **檢查點盡量往上游放。** 能在文字階段判斷的事,絕不等到音訊生成後才檢查——修復成本沿著 pipeline 是階梯式跳升的。
4. **能用結構約束的,就不要靠 prompt 祈禱。** 立場強度、限定語、揭露內容都做成 beats 的獨立欄位加固定句式,而不是在 prompt 裡寫一段「請忠實反映原文」。

**成本**:上架免費;TTS 走本地開源模型,零 API 費用;主要成本是腳本生成的 LLM 呼叫,以及一次性的工程建置。

## 核心設計原則

這四條貫穿所有階段,遇到設計取捨時回來看這裡。

**原則一:Single source of truth**

音訊內容的唯一來源是部落格文章。這比「不要幻覺」更嚴格:

| 情境 | 只防幻覺 | Single source of truth |
|---|---|---|
| LLM 編造一個不存在的數字 | 擋下 | 擋下 |
| LLM 補充「ReAct 是 2022 年提出的」(屬實,但文章沒寫) | 放行 | **擋下** |

判斷依據不是「這句話對不對」,而是「這句話能不能對應回文章某一段」。後者可自動化,前者不行。

**原則二:Fail fast**

修復成本沿 pipeline 遞增,且是階梯式跳升:

| 發現問題的階段 | 要重跑什麼 | 相對成本 |
|---|---|---|
| 逐字稿階段 | 一次 LLM 呼叫 | 1 |
| TTS 之後 | 整段語音重新合成 | 10 |
| 後製之後 | 重新合成 + 重新拼接正規化 | 30 |
| 上架之後 | 全部重來 + 撤下已發布集數 + 平台違規紀錄 | 極高,部分不可回收 |

**規則:檢查放在「能夠判斷這件事的最早時間點」。** 揭露句是否合規、數字有無幻覺,在文字階段已能百分之百判斷,就沒有理由等到音訊生成後。

**原則三:結構約束優於 prompt 指示**

LLM 對「請保持懸念」「請忠實反映語氣」這類軟性指示的遵循率不穩定。把要求變成結構化欄位加固定句式,可靠度高一個量級。

實例:立場保真不靠 prompt 描述,而是在 beat 上標記 `陳述強度`,並為每種強度指定固定的口語模板。

**原則四:形式與內容分離**

「文章講了什麼」(beats)與「怎麼把它說出來」(逐字稿)是兩次獨立的 LLM 呼叫。這是未來雙人對談擴充的關鍵:只需重寫渲染層,beats 層完全複用。

## 一、節目定位

| 項目 | 決定 | 理由 |
|---|---|---|
| 目標聽眾 | 同領域的 AI 研究者 / 工程師 | 部落格的價值在於誠實指出論文缺口,這是給同行的視角,稀釋成大眾向反而失去優勢 |
| 格式 | 單人口白起步,保留雙人擴充 | 不依賴他人配合;雙人版對 prompt 工程要求高得多,容易生出「為對話而對話」的灌水內容 |
| 單集長度 | 目標 15-20 分鐘 | 不逐字唸完全文;前幾集刻意壓在 12-18 分鐘先練順流程 |
| 一篇文章的處理 | 精華版優先,超長文章可拆上下集 | 高密度數據硬塞進單集,會被迫用快語速唸過所有數字,聽眾反而抓不到重點 |
| 更新頻率 | 跟隨部落格節奏,寧可慢而穩定 | 規律更新的普通節目,長期表現勝過不定期更新的優質節目 |
| 語言 | 繁體中文為主,英文版延後推出 | 英文市場觸及面大但競爭激烈;beats 架構讓英文版可隨時回頭批次補生成,晚做無損失(見第八章) |
| 商業模式 | 初期不設贊助連結,之後再考慮業配 | 但音樂授權現在就選「允許商業使用」,避免未來返工 |

## 二、Pipeline 總覽

```
[1] 部落格文章
  -> [2] 內容抽取 Agent(LLM)
    -> [3] beats.json(結構化,非逐字稿)
      -> [4] 長度裁切(純程式邏輯)
        -> [5] 語音渲染 Agent(LLM)  <- 分支點:單人中文 / 單人英文 / 雙人(未來)
          -> [6] 逐字稿
            -> [7] 檢查層 1:文字面(硬性 gate)
              -> [8] TTS 分段合成
                -> [9] 檢查層 2:音訊面(產出報告)
                  -> [10] 拼接 + 音量正規化 + 片頭尾
                    -> [11] final.mp3 + show notes
                      -> [12] 手動上傳
```

### 檔案結構

```
episodes/
  <slug>/
    beats.json           # 中間表示法(語言中立,兩版共用)
    metadata.json        # 版本追蹤
    zh/
      script.txt         # 送 TTS 前的最終逐字稿
      segments/          # TTS 輸出的片段
        b00_hook.wav
        b01_identity.wav
        ...
      assembled.wav      # 拼接後、正規化前
      final.mp3          # 成品
      shownotes.md       # 含時間戳
    en/                  # 結構同上,延後建立
```

語言分層放在 `beats.json` 之下,是因為 beats 是兩版共用的唯一真理來源;逐字稿以下的所有產物都是語言相關的。

保留所有中間產物的價值:某個 beat 唸壞時只需重生該片段再重跑拼接,不必整集重來。

## 三、腳本生成

> **本章已被取代。** 實際判準以 `reference/NARRATION.md` 與
> `.claude/skills/podcast/SKILL.md` 為準,它們比這章具體得多,而且是從
> 實際踩過的坑長出來的。這章留著看當初的推導,不要照著執行。

### 3.1 為什麼要有 beats 這一層

beats 不是腳本。這個區分是整個設計的基礎:

| | beats | 逐字稿 |
|---|---|---|
| 內容 | **要講什麼**的結構化清單 | **實際會被唸出來的每一個字** |
| 形式 | JSON,條列、精簡、無語氣 | 連續口語文字,有語氣與轉折 |
| 消費者 | 下一個 LLM(渲染 Agent) | TTS 引擎 |
| 單人/雙人差異 | **完全相同,共用一份** | 完全不同,各自生成 |

類比:beats 是廚房備料,逐字稿是上桌的菜。同一批備料可以做成單人簡餐或雙人合菜。

**四個具體收益**:

1. 雙人擴充只需重寫渲染 prompt,不必重新分析文章,也避免兩版本對「什麼是重點」判斷不一致。
2. **英文版同理**:beats 記錄的是「要講什麼」而非「怎麼講」,本質上是語言中立的,英文渲染 Agent 可直接消費同一份 beats(見第八章)。
3. 品質檢查在精簡的 beats 上做,成本遠低於在完整逐字稿上比對原文。
4. 每個 beat 帶 `預估秒數`,長度控制在生成逐字稿**之前**用程式完成,而非生完才發現超長。

### 3.2 開場順序(留存率關鍵)

podcast 的聽眾流失最集中在開頭。正確順序是**先勾住,再自我介紹**:

```
[片頭音樂 8-12s] -> [b00 hook 15s] -> [b01 節目識別 + AI 揭露 10s] -> [b02 正文]
```

約 35 秒進入正文。反過來先自我介紹再進主題,會在聽眾還沒有理由留下時就消耗掉他的耐心。

### 3.3 hook 的特殊設計

hook 的任務不是傳遞資訊,而是製造想聽下去的理由,因此需要專屬欄位:

```
{
  id: "b00",
  type: "hook",
  重要度: "must",
  預估秒數: 15,              // 硬上限
  鉤子類型: "反直覺結果",
  內容: "...",
  來源beat: "b07",           // 取材自哪個 beat
  不可劇透: true
}
```

**`鉤子類型` 是給抽取 Agent 的選項清單**,讓它有明確依據而非自由發揮:

| 鉤子類型 | 使用時機 |
|---|---|
| 反直覺結果 | 有違反預期的實驗數據 |
| 論文的破綻 | 作者有批判性發現 |
| 具體痛點 | 讀者有共鳴的實務問題 |
| 數字衝擊 | 有夠大的效果量 |

**`不可劇透` 為何需要獨立欄位**:LLM 生成 hook 的預設傾向是把結論一起講完(它被訓練成要提供完整資訊),結果變成摘要而非鉤子。

```
✗ 摘要式:「這篇論文發現讓 Skill Proposer 存取 wiki 能提升 15 分,
          因為跨迭代知識累積能幫助處理複雜失敗模式。」
○ 鉤子式:「同樣一份知識庫,給 A 看能加 15 分,給 B 看反而扣分。差別在哪?」
```

**衍生的裁切約束**:被 hook 引用的 beat(`來源beat`)自動升級為 `must`,不可裁切。否則聽眾被勾住的問題整集都沒有答案。裁切前掃一遍 hook 的 `來源beat` 欄位即可實作。

### 3.4 視覺元素的處理

閱讀是隨機存取的,聽覺是線性的。讀者可來回掃視表格,聽眾只有一條時間軸。因此視覺元素不能「翻譯」,必須「重寫」。

**第一類:對照型表格 → 抽出 1-2 組核心對比**

聽眾需要的不是五個數字,而是表格背後的結論。

```
原始:五列消融實驗數據
改寫:「打開 Proposer 的 wiki 存取權,分數從 48.7 跳到 63.7」
     「反過來讓 Inference Agent 也看 wiki,分數反而從 63.7 掉到 60.9」
```

**口語敘述數字的鐵則:一次只比較兩個數,且明講「從什麼變成什麼」。**

**第二類:架構圖 / 流程圖 → 改寫成時間順序的敘述**

圖是空間的,語言是時間的。不要描述圖的長相(「上面是 Skill 層,中間是 Wiki 層」——聽眾無法建構這個畫面),要描述資料如何流動:

```
「一次迭代是這樣跑的:先讓 agent 用現有 skill 去跑訓練任務,
  把過程原封不動記下來。接著有一個角色會去抽樣看幾筆紀錄,
  分析失敗原因,寫進一個持久的知識庫。然後另一個角色讀這個
  知識庫,提出 skill 修改建議。最後跑驗證,有進步就採用,
  沒進步就整組退回。」
```

**第三類:公式 / 程式碼 → 只講行為與後果,不呈現符號**

沒有人能靠耳朵理解一個公式。

```
原始:(1 + T_ReAct) × (N_train / B)
改寫:「呼叫次數只跟 ReAct 輪數有關,跟訓練集大小完全無關。
      所以訓練集從 80 筆變成 800 筆,每輪呼叫次數不變,
      但另外幾個方法都會線性增加。」
```

**第四類:交叉引用(「如表 1 所示」)→ 一律刪除**

聽眾看不到表 1,這是純噪音。唯一可接受的替代是指向文字版:「這組數字比較細,有興趣可以看部落格原文。」——順便完成導流。

### 3.5 量化結果的取捨

目標聽眾是同行,數字本身就是可信度來源。聽到「效果顯著」卻沒有數字,同行會懷疑論述空洞。因此框架不是「少講數字」,而是**「哪些數字值得佔用聽眾的注意力預算」**。

**保留優先序**:

1. **證明主要主張的那一個數字** — 必留,這是骨幹
2. **反直覺的數字** — 必留,聽眾記得住,且是節目的價值所在
3. **支撐批判觀點的數字** — 必留,沒有數字批判就站不住
4. **同類重複的佐證** — 砍,講一組即可,其餘改成「其他任務也看到類似幅度」

**一句話**:留下「改變聽眾想法的數字」,砍掉「只是再確認一次的數字」。

**數字的口語化處理**:

- 核心數字保留小數,其餘四捨五入:「從大約 49% 拉到 64%」
- **必須給差值,不只給端點**:「進步了 15 個百分點」比讓聽眾心算好
- 給對照錨點:「這是全文最大的單一變因效果」——有排名聽眾才知道大小
- 上限建議:整集不超過 6 組數字對比,超出的降級為 `optional`

**重要數字要重述**:寫作忌諱重複,口語相反。核心數字一集出現 2-3 次是合理的(講述時、段落收束時、結尾帶走的東西再提一次)。這要明確寫進渲染 prompt,否則 LLM 會本能避免重複。

### 3.6 專有名詞的首次處理

讀者看到英文可以自行消化,聽眾聽到一串英文會卡住。

**規則:第一次出現時先講中文功能描述,再給英文名稱**,之後可直接用英文短名。

```
「有一個角色專門負責提出 skill 的修改建議,論文叫它 Skill Proposer。」
```

beats 需帶 `首次出現術語` 欄位記錄對照。

**此欄位僅中文版適用。** 英文版不需要這層處理(Skill Proposer 對英文聽眾就是字面意思),渲染時應忽略該欄位。

### 3.7 長度控制

**秒數估算**:不要讓 LLM 估,用字數換算。

```
中文口語約每分鐘 220-260 字(TTS 預設語速)-> 每秒約 4 字
預估秒數 = 展開後預期字數 / 4
```

陷阱:beats 寫的是要點,逐字稿是展開後的內容,字數差距大(要點 30 字可能展開成 150 字)。**跑過幾集後量出自己的展開倍率**(例如 4.5 倍),之後用該係數估算即可穩定。

**裁切順序**:`must` 全收 → 依序補 `should` → 落入目標區間即停。若 `must` 本身超過上限,代表抽取階段判斷太寬鬆,應回頭調整而非硬砍 must。

**避免裁切造成斷層**:`銜接前一個beat` 欄位不應在抽取階段寫死,而應由程式在裁切完成後,依實際相鄰關係動態填入。否則被砍掉的 beat 會留下懸空的轉場。

### 3.8 品質把關

#### 檢查層 1:文字面(硬性 gate,不通過不得往下)

**維度一:數字保真**(可完全自動,近乎零誤判)

```
1. 從文章 regex 抽出所有數字 -> 集合 A
2. 從逐字稿抽出所有數字 -> 集合 B
3. B 的每個數字必須能對應到 A 中某數字的原值或四捨五入
4. 任何無法對應的數字 -> 立即擋下
```

允許四捨五入是必要的例外(原文 48.7,逐字稿講「大約 49」)。

**維度二:無出處句子檢查**(single source of truth 的主要執行手段)

將逐字稿切成句子,逐句判斷「這句的資訊能否在文章中找到依據」。需以 beat 的 type 事先排除三類例外,否則誤報率過高:轉場句、揭露句、純口語連接詞。

**維度三:限定語保真**

對每個帶 `必須保留的限定語` 的 beat,檢查對應逐字稿段落是否保留等價表述。需要一次額外的 LLM 呼叫作為 verifier。

**重要設計約束:verifier 不可與生成共用 context。** 只給它乾淨輸入(原文片段 + 生成片段),讓它獨立判斷。若讓它看到生成過程的 context,它會傾向認同自己剛才的產出。

**維度四:立場保真**

文章明確區分三種陳述,而 LLM 口語化時最常見的失真就是把三者壓平成同一種肯定語氣。解法是結構化欄位加固定句式:

```
陳述強度: "已證明" | "論文主張未證明" | "作者推論"
```

| 陳述強度 | 固定口語模板 |
|---|---|
| 已證明 | 「實驗顯示……」「數據上……」 |
| 論文主張未證明 | 「論文主張……但這點其實沒有被驗證」 |
| 作者推論 | 「我自己的看法是……」「這裡是我的解讀……」 |

**維度五:揭露句合規**

檢查揭露句是否明確包含「聲音是 AI 生成」這個資訊。放行的前提是這句話不能委婉到聽眾聽不出來(例如「本集有 AI 協助製作」不算充分揭露)。不通過則重新生成該句。

**此檢查必須放在 TTS 之前。** 這是 fail fast 原則最直接的應用:揭露句是否合規,在文字階段已能完全判斷,音訊不提供任何額外資訊。

#### 檢查層 2:音訊面(初期產出報告,不自動擋下)

只有文字階段看不出來的才放這層:

- 實際總時長(TTS 語速影響,文字階段只能估算)
- 中英混雜術語的發音正確性
- 音量是否符合標準

初期做成報告供人工檢視;累積足夠經驗、確認哪些問題會反覆出現後,再把可自動化的部分升級為硬性 gate。

#### 自動化程度的誠實評估

| 檢查維度 | 可信任程度 |
|---|---|
| 數字保真 | 完全可自動化 |
| 無出處句子 | 可自動化,需調校例外規則 |
| 限定語保真 | 勉強,建議初期人工複核 |
| 立場保真 | **不建議完全自動化** |

**至少前十集,建議人工讀過逐字稿再送 TTS。** 目的是累積「LLM 在哪些地方固定出錯」的樣本,再把那些 pattern 固化成自動檢查。

### 3.9 文章版本追蹤

文章日後可能修正錯字、補充內容、更正判斷。一旦音檔上架而文章又改動,兩者就對不上。

`metadata.json` 記錄每集所依據的文章版本:

```json
{
  "source_url": "https://datasciocean.com/paper-intro/<slug>/",
  "source_modified_at": "...",
  "generated_at": "...",
  "tts_model": "...",
  "script_hash": "sha256:..."
}
```

成本近乎為零,但沒記就永遠查不回來。

## 四、TTS 語音合成

> **本章已被取代。** 選型早已定案(Gemini TTS 走 OpenRouter + Zubenelgenubi),
> 過程見 `RESEARCH-HISTORY.md`,實測陷阱見 `reference/GEMINI-TTS.md`。
> 這章的候選比較是決定之前的猜測,不是結論。

### 4.1 選型的前提

**公開 TTS 排行榜對本專案幾乎沒有參考價值。** 主流評測(如 Artificial Analysis Speech Arena)只評估英文音訊。本專案的需求是「繁體中文為主、密集夾雜英文技術術語」,在任何公開榜單上都沒有對應評測項目。

**因此選型結論只能來自自行實測。** 測試集見附錄 C。

**Mac 環境的第一道篩選是 MLX 支援度。** MLX 是 Apple 的機器學習框架,直接跑在 Apple Silicon 的統一記憶體 GPU 上。沒有 MLX 移植的模型只能走 PyTorch MPS 後端,速度較慢且較易遇到記憶體問題。

**中文版與英文版應各自獨立選型,不必共用同一個引擎。** 下列 4.2 至 4.5 的討論全部針對中文版;英文版的選型條件完全不同,見 8.4。

### 4.2 候選比較

| 順位 | 模型 | 選它的理由 | 主要風險 |
|---|---|---|---|
| 1 | **Qwen3-TTS** | Apache-2.0,授權最乾淨;MLX-Audio 支援;阿里持續維護 | 有使用者反映英文帶中文腔 |
| 2 | **IndexTTS-2 / 2.5** | 中英混合最對症;MLX 生態最成熟;支援精確時長控制 | **權重為非商業授權** |
| 3 | **VibeVoice 1.5B** | 原生支援長篇單次生成與多說話者,雙人擴充直接受惠 | 微軟已從官方 repo 移除 TTS 程式碼;中文穩定性有已知問題;會自發生成背景音 |
| 4 | **CosyVoice2-0.5B** | 最輕量,保底方案 | 品質天花板較低 |

**授權細節(重要)**:IndexTTS-2 的權重採 INDEX_MODEL_LICENSE,商業使用需取得 bilibili 書面授權(聯絡 indexspeech@bilibili.com);移植與推論程式碼本身為 Apache-2.0 / MIT。注意 HuggingFace 上部分頁面標示 apache-2.0,那是指初代 Index-TTS 或程式碼部分,與 IndexTTS-2 權重的授權不同。

**關於「英文帶中文腔」**:這對本專案未必是缺點。節目是台灣工程師講中文夾英文術語,真人講起來本就帶中文腔;純美式發音突然出現在中文句子裡,可能反而突兀。此項需靠實際試聽判斷。

**VibeVoice 的三個具體風險**:微軟因發現不符原始意圖的使用方式而移除程式碼(現需走社群 fork),這是專案永續性的紅旗,性質與 Coqui 收掉 XTTS-v2 相同;社群 repo 自承中文合成有偶發不穩定,建議中文文字也使用英文標點且僅用逗號句號;官方 FAQ 說明背景音樂是自發產生的、無法直接控制——對技術類 podcast 可能造成嚴重干擾。

### 4.3 建議的實測順序

```
[1] 先跑 IndexTTS-2 -> 目的是建立品質基準線,而非選定它
  -> [2] 用 C 組(中英交界)測試句先做淘汰測試
    -> [3] 過關才續測 A/B/D/E 組
      -> [4] 再試 Qwen3-TTS,與基準線比較
        -> [5] 都不理想才回頭考慮雲端 API
```

**為何從 C 組開始而非依序**:C 組(中英交界斷句)是唯一無法補救的失敗類型,先測它等於先做淘汰測試。一個引擎若在 C 組崩潰,其餘表現再好也無用。與 pipeline 的 fail fast 是同一思路。

**為何先跑 IndexTTS-2 卻不打算長期採用**:需要先知道「最強的中英混合模型能做到什麼程度」,之後聽 Qwen3-TTS 的輸出才有判斷依據。與測試集裡放送分題建立基準線是同樣的道理。

### 4.4 發音修正的三個層次

| 層次 | 手段 | 評價 |
|---|---|---|
| 1 | 自訂發音詞典 | **最推薦**,作用在 TTS 層,不污染逐字稿 |
| 2 | SSML 標記(`<lang>` 強制語言、`<break>` 控制停頓) | 可用,但 pipeline 需多一層標記處理 |
| 3 | 改寫逐字稿 | **不建議常態使用**,會讓音訊偏離文章,違反 single source of truth |

需建立的發音詞典初始清單:

```
ReAct, Grep, Glob, Qwen, BERT, distilbert, harness,
Proposer, Maintainer, trace, MCP, LLM, RLHF, SFT, ROUGE,
CLAUDE.md, rm -rf, fallback, fuzzy match
```

### 4.5 長文本分段

20 分鐘的稿子不應一次送進 TTS,原因有三:多數 API 對單次請求有長度上限;單次生成越長,失敗重試成本越高;部分模型長文本會出現語調漂移(後半段語速或情緒與前段脫節)。

**以 beats 作為天然切分邊界**,每個 beat 獨立合成一個片段。三個好處:某個 beat 唸壞只需重生該段;片段間停頓由程式以靜音填充控制,比讓 TTS 自行決定穩定;未來雙人版本不同角色本就需分開合成,架構直接沿用。

### 4.6 抽換性設計

開源 TTS 生態有維護中斷的前例。**TTS 層應設計成可抽換的介面,不與特定模型綁死。**

實作建議:`mlx-audio` 提供 OpenAI 相容的 REST API。將 TTS 層寫成呼叫 OpenAI 格式的介面,底層換模型甚至換成雲端 API,上層程式碼皆不需更動。

## 五、音訊後製

### 5.1 拼接與停頓設計

```
片頭音樂 -> [靜音 0.5s] -> hook -> [靜音 0.6s] -> 節目識別+揭露
  -> [靜音 0.8s] -> beat -> [靜音 0.6s] -> beat -> ...
    -> [靜音 1.0s] -> 片尾 -> 片尾音樂
```

| 位置 | 靜音長度 | 理由 |
|---|---|---|
| 段落之間(同主題內) | 0.4-0.6 秒 | 讓聽眾喘息,不中斷思緒 |
| 章節之間(換大主題) | 0.8-1.2 秒 | 建立明確段落感 |
| 音樂與人聲之間 | 0.3-0.5 秒 | 避免撞在一起 |

**停頓應由程式控制而非交給 TTS**,因為 TTS 的句末停頓不穩定,同模型不同段落可能差異很大。

> ⚠️ 原文這裡的 pydub 範例**不要照做**。pydub 處理非 wav 格式要 ffmpeg,
> 正是本專案刻意避開的系統依賴。實作見 `pipeline/stitch.py`,
> 靜音就是 `np.zeros(int(gap * sr))`,不需要任何套件。

### 5.2 音量正規化

新手最常漏掉、聽眾感受卻最直接的一環。節目音量若低於其他節目,聽眾在播放清單中切換時需手動調整,體驗很差,且平台可能自行調整導致更不可控。

**LUFS 是什麼**:Loudness Units relative to Full Scale。與一般音量(峰值 / dB)的差異在於,它衡量的是**人耳感知到的平均響度**,而非波形最大值。兩段峰值相同的音訊,人耳聽起來可能差很多。

**podcast 業界標準:-16 LUFS(立體聲)/ -19 LUFS(單聲道)。**

| 指標 | 目標值 | 意義 |
|---|---|---|
| Integrated Loudness | -16 LUFS | 整集平均感知響度 |
| True Peak | ≤ -1 dBTP | 最大瞬間值,留 headroom 避免壓縮後破音 |
| Loudness Range (LRA) | 約 5-8 | 最大聲與最小聲的差距,語音類不需太大 |

```
ffmpeg -i input.wav -af loudnorm=I=-16:TP=-1:LRA=7 output.wav
```

**建議採兩階段(two-pass)處理**:第一次分析取得實際數值,第二次才套用修正。單次處理準確度明顯較差。

### 5.3 可以跳過的後製

因為來源是 TTS 而非真人錄音,以下真人 podcast 必做的項目可直接省略:

- **降噪** — TTS 輸出無環境噪音
- **去除贅詞** — TTS 不會產生
- **EQ 調整** — TTS 輸出頻率響應通常已很乾淨
- **壓縮器** — LUFS 正規化已涵蓋大部分需求

這是自動化 pipeline 的實質優勢:後製只剩「拼接 + 正規化 + 加頭尾」三件事,全部可腳本化。

## 六、品牌素材

### 6.1 開場音樂

**規格**:8-12 秒。過長聽眾會想跳過。

**一旦選定就不要更換。** 品牌識別靠重複,聽眾聽過三集後,那 8 秒會變成「是這個節目」的條件反射。

**三個通用限制(AI 音樂工具最常踩的坑)**:

- 避免 epic cinematic — AI 音樂工具的預設傾向是往「電影預告片」走,氣質與知識型節目不合,且每集聽會疲勞
- 避免 vocals — 人聲會與口白打架
- 要求 clean ending — 結尾收乾淨才好與人聲銜接

三個方向的完整 prompt 見附錄 B。

**若改用現成音樂庫**,搜尋關鍵字組合:

```
curious / playful / quirky      <- 情緒(避開 epic、inspiring)
technology / science / podcast  <- 用途
marimba / synth / lo-fi         <- 樂器
intro / logo / stinger          <- 長度類型
```

**「stinger」值得記住**,音樂庫中專指 5-15 秒的短片段,直接搜此詞比搜 "background music" 精準得多。

**授權**:必須為免版權(royalty-free)且**允許商業使用**(即使初期不接贊助,先選商用授權可避免未來返工)。來源可考慮 Free Music Archive、Pixabay Music,務必逐一確認授權條款。

**銜接技巧**:片頭音樂淡出時與人聲重疊 1-2 秒(音樂降至約 -30 dB 作背景),比硬切自然。

> ⚠️ **不要用 pydub**(沒裝,也不該裝 —— 它需要 ffmpeg)。淡出是乘一條窗函數、
> 疊加是對齊後相加,numpy 兩行就夠:
> `music[-n:] *= np.linspace(1, 0, n)` 然後 `out[i:i+len(m)] += m * 10**(-30/20)`。
> 混音腳本還沒寫,寫的時候照這個做。

### 6.2 開場與片尾說辭

**狀態:待節目主持人自行撰寫。**

這部分不建議由 AI 生成或套用模板。開場白承載的不是資訊而是語氣,是節目人格的直接體現,由本人書寫的效果會明顯優於任何生成版本。過度工整、每句都在完成某個功能的文案,聽起來會像機器人念稿。

撰寫時建議滿足的功能(而非句式):

**開場(固定部分)**需要傳達:
- 這個節目與其他論文導讀的差異在哪
- 節目的視角是並肩探究而非講台宣告

**開場(變動部分)**需要包含:
- 當集主題
- AI 揭露(見 7.3)

**片尾**需要傳達:
- 導流回部落格,且**理由要具體**——明講「完整的表格與數據都在文章裡」,這正是音訊格式做不到的事,比籠統的「歡迎來我的部落格」有效
- 初期不放贊助連結
- 不使用「訂閱、按讚、開啟小鈴鐺」這類 YouTube 語法,目標聽眾對此反感度高

**若日後要加訂閱提醒**,建議放在片頭之後、正文之前,而非片尾——podcast 聽眾在最後幾秒的流失率很高。

**技術建議**:固定的開場白**錄一次存成獨立音檔重複使用**,不要每集讓 TTS 重新生成。TTS 每次輸出有細微差異,固定音檔的一致性才能形成識別,同時省下每集的合成時間。

### 6.3 節目封面

3000×3000 像素、正方形、JPG 或 PNG。此規格 Apple 與 Spotify 通用,一次做好兩邊可用。

## 七、發布與合規

### 7.1 上架方式

Apple Podcasts 與 Spotify 上架本身皆免費。**兩者都未提供給個人創作者的公開上傳 API**,因此上傳、填寫標題描述、發布這幾步需手動完成。

**初期採用手動上傳。** Spotify for Creators(前身 Spotify for Podcasters)提供無限儲存空間、無月費,並自動產生 RSS feed,該 feed 網址可直接提交至 Apple Podcasts Connect,一份 hosting 服務兩邊通用。

**未來若要全自動化**,可改為自架 RSS feed(音檔放 S3/R2/GitHub Pages,自行產生 XML)。因為平台是定期讀取 RSS feed 抓取新集數,pipeline 直接寫入 XML 即可免手動。代價是需自行處理 CDN、頻寬與 RSS 正確性。**不建議在摸索階段做此遷移**——更換 hosting 會變更 feed 網址,需在舊 feed 設定 redirect,是需謹慎處理的遷移作業。

### 7.2 RSS metadata

**節目層級(設定一次)**:

```
title:        DataSci Ocean
description:  節目簡介(200 字內)
language:     zh-TW          <- 注意勿填 zh-CN
category:     Technology
explicit:     false
author:       (節目主持人)
image:        3000x3000 封面
```

`language` 填錯會影響平台分類與推薦,而多數範例寫的是 `zh-CN`。此欄位只能填單一值,這正是英文版必須另開獨立節目的原因(見第八章)。

**單集層級(每集)**:

```
title, description, pubDate,
enclosure(音檔 URL + 檔案大小 + MIME type),
duration, episode
```

### 7.3 AI 揭露(合規要求)

**Apple Podcasts 第 1.11 條**明文規定:以 AI 生成音訊或影片內容(包含合成語音、AI 生成的主持人角色)者,必須在**內容本身**與 **metadata** 兩處清楚揭露。本專案完全符合此條件,非模糊地帶。

**Spotify** 目前對 podcast 無強制標籤機制,原則為不欺騙聽眾、不侵權、保有人類監督,但仍保留下架權利。

**未揭露的後果**:Apple 對違反內容準則的集數或節目可能下架;重複違規或同時觸及其他條款(如第 1.12 條誤導性內容)時,帳號可能被限制。此條款位於「不實、誤導或未授權內容」分類下,屬正式規則。

**風險評估**:揭露成本極低(腳本開頭一句話),風險高度不對稱(賭贏無所得,賭輸整集或整個節目被下架)。不值得規避。

**音訊版揭露(採用文字)**:

> 本集音訊由 AI 語音合成,內容改編自我的部落格文章。

此措辭的取捨說明:嚴格讀 Apple 規則,腳本亦屬 AI 生成、也在揭露範圍內。僅寫「本集音訊由 AI 語音合成」已涵蓋聽覺媒介中最關鍵、最可能誤導聽眾的事實(聲音不是真人),但加上「內容改編自我的部落格文章」多花幾個字即可一併說明內容來源為人類,同時對聽眾傳達「內容有人負責」的訊息,判斷為划算。

**生動化的做法**:不必每集念同一句制式聲明。在 `b01` beat 中不寫死文字,而是給渲染 Agent「必須傳達的事實 + 語氣要求 + 長度上限」,並允許它與當集主題呼應。與主題呼應的揭露句不再是可跳過的公告,而成為內容的一部分。

**metadata 版揭露**:相反地,建議**寫死固定文字**。這是文字、不會被聽,不需要變化,固定反而更明確、更好稽核。

**發布前最後一道 gate**:確認音訊與 metadata 兩處揭露皆存在,才允許發布。漏掉的代價是整集下架。

### 7.4 Show notes 自動生成

可完全自動化,beats 即現成素材:

```
[一句話摘要]
[3-5 個重點條列]   <- 從 must beats 的「核心主張」抽出
[時間戳記]         <- 拼接階段即已知每段起始秒數
[原文連結]
[AI 揭露聲明]      <- 固定文字
```

**時間戳記值得特別做**:拼接階段已知每個片段長度,累加即得,幾乎零成本。對聽眾實用(可跳至想聽的段落),部分平台會直接渲染為可點擊章節。

### 7.5 版權音樂

Spotify 使用條款禁止上傳不屬於自己的音訊內容。配樂與音效須使用免版權音樂庫或已取得授權的素材,否則可能被下架或收到侵權通知。

## 八、英文版

### 8.1 硬性限制:必須是兩個獨立節目

RSS 規格的 `<language>` 是節目層級的單一欄位,只能填一個值。實務上已有創作者因節目混用多種語言而被 Apple 以「Incorrect Language」為由退件。

因此雙語必然是兩個獨立節目:

```
DataSci Ocean            (zh-TW)  <- 中文節目,獨立 feed
DataSci Ocean [English]  (en)     <- 英文節目,獨立 feed、獨立提交
```

兩邊各自上架、各自累積訂閱數,聽眾不會互相看到。這是平台限制,沒有繞路方式。

### 8.2 關鍵設計決定:從 beats 生成,不翻譯逐字稿

| | 翻譯中文逐字稿 | 從 beats 直接生成英文 |
|---|---|---|
| 語感 | 帶翻譯腔(translationese),句構仍是中文的 | 原生英文語感 |
| 口語節奏 | 中文的節奏套在英文上,聽感彆扭 | 符合英文 podcast 的表達習慣 |
| 溯源檢查 | 需多一層(英文 → 中文 → 文章) | 直接對回文章 |
| 錯誤傳播 | 中文稿的錯誤會原封不動帶進英文 | 兩版獨立,一版錯不影響另一版 |

**採用後者。** beats 存的是「要講什麼」而非「怎麼講」,只要 `核心主張`、`支撐細節` 等欄位夠結構化,英文渲染 Agent 可直接消費。

### 8.3 需要調整的部分

**beats 層**:唯一需要語言標記的是 `首次出現術語`,標記為僅中文版適用。其餘欄位兩版共用。

**檢查層 1**:數字保真、無出處句子、限定語保真、立場保真四個維度全部照舊適用,只是比對的是英文逐字稿對中文文章。溯源判斷需要跨語言,verifier 的 prompt 要相應調整。

**品牌素材**:音樂可共用(這是唯一能省的);節目名、簡介、封面文字、開場白、片尾皆需獨立的英文版本。

### 8.4 意外的紅利:英文版技術上簡單得多

**C 組測試(中英交界斷句)那整類問題在英文版完全不存在。** 純英文 TTS 是所有引擎最成熟的能力,可選模型也多得多,包含 Kokoro 這類極輕量的英文專用模型(82M 參數,速度快數倍)。

現實推論:**英文版的合成品質很可能優於中文版,且更快、更穩。** 選型時不必沿用中文版的引擎,應獨立評估。

### 8.5 現實評估

**工作量是加倍,不是免費。** 雖然 beats 複用,但仍需:多一組品牌素材、多一次 TTS 合成與後製與檢查、多一個平台帳號與手動上傳、兩邊各自生成 show notes。

**英文市場競爭激烈得多。** 中文市場的 AI 論文解讀幾乎沒有對手;英文市場有大量同類節目,且不乏製作精良者。既有的差異化(誠實指出論文缺口的批判視角)在英文市場仍然成立,但**曝光難度高一個量級**。

**判斷**:值得做,但應視為長期的觸及面投資,而非短期的訂閱數捷徑。不應期待英文版一開始就有更好的成效。

### 8.6 推出順序

**不要一開始就雙語並行。** 理由與「第一集不要用最好的文章」相同:pipeline 仍在調校時同時維護兩條線,會難以分辨問題出在架構還是語言。

```
[1] 中文版跑順(約 5-10 集)
  -> [2] 用同一批 beats 補生成英文版
    -> [3] 英文版可「補發」前面幾集,不必從第一集重來
```

第 3 點是實質優勢:**beats 全部保留,英文版隨時可回頭批次生成過去的集數。** 因此晚開英文線沒有任何損失,不需要急。

## 九、上線路徑

### 建置順序

```
[1] 跑 TTS 測試集,選定引擎          <- 一小時內可得初步結論
  -> [2] 手工做一集(不寫程式)       <- 驗證內容轉譯是否可行
    -> [3] 實作 beats 抽取 + 渲染
      -> [4] 實作檢查層 1
        -> [5] 實作拼接與正規化
          -> [6] 上架第一集
            -> [7] 累積十集後,把反覆出現的問題固化為自動檢查
```

**第 2 步(手工做一集)不應跳過。** 在寫任何程式之前,先用手工方式走完一次完整流程,才知道哪些環節真的需要自動化、哪些是想像出來的問題。

### 第一集的選擇

**不要用最得意的文章當第一集。** 前幾集必定會遇到 TTS 唸錯、節奏不順、長度失控等問題,而第一集通常是新聽眾的入口、會被聽最多次。建議選一篇自認普通的文章先把流程跑順,好內容留到第三、四集。

### 集數標題

podcast 的發現機制很大程度依賴標題。既有的部落格標題風格已經合適——有動詞、有懸念、不只是論文名。應直接沿用,避免退化成「第 5 集:某某論文解讀」這類形式。

**具體建議:把論文名放在標題後半而非最前面。** podcast app 的列表會截斷標題,前幾個字最珍貴,應留給能勾起好奇的部分。

### 上線後的驗證

**找一個人聽第一集,全程不解釋、不辯護。** 觀察他皺眉、分心、想跳過的時刻,特別注意他**什麼時候拿起手機**——那就是內容失去他的時刻。這比任何檢查清單提供的資訊都多。

### 長期經營

**一致性比單集品質更重要。** 對新頻道而言,規律更新的普通節目長期表現會勝過不定期更新的優質節目,演算法與聽眾習慣都獎勵可預期性。

設定一個確定做得到的頻率,寧可兩週一集也不要承諾每週然後斷更。自動化 pipeline 一旦跑順,維持頻率的成本遠低於真人錄音——這是本專案最該珍惜的競爭優勢。

## 附錄 A:beats 完整結構定義

> **已被實際 schema 取代**,見 SKILL.md 步驟 3。這裡的欄位設計理由仍可讀。

### 一般 beat

```
{
  id: "b04",
  type: "實驗發現",
  重要度: "must",              // must / should / optional
  預估秒數: 60,

  核心主張: "只讓 Skill Proposer 存取 wiki,平均分數從 48.7% 跳到 63.7%",

  支撐細節: [
    "只用單一模型做",
    "+15.0 個百分點,是全文最大的單一變因效果"
  ],

  陳述強度: "已證明",           // 已證明 / 論文主張未證明 / 作者推論

  聽眾可能的疑問: "為什麼只讓 Proposer 看,不讓 Inference Agent 看?",

  必須保留的限定語: "這是消融實驗,只在單一模型上驗證",

  首次出現術語: [                // 僅 zh 版適用,英文版渲染時忽略
    { 詞: "Skill Proposer",
      口語化: "負責提出 skill 修改建議的那個角色" }
  ],

  視覺依賴: "表 3",             // 供人工核對,不進入逐字稿
  口語化提示: "數字太密,只講 48.7 到 63.7 這組",

  來源段落: "5. 消融實驗:wiki 到底在哪裡起作用",
  來源原文摘錄: "...",          // 供溯源檢查

  銜接前一個beat: null          // 由程式在裁切後動態填入
}
```

### 欄位設計理由

| 欄位 | 為何需要 |
|---|---|
| `聽眾可能的疑問` | 雙人版的燃料——直接作為「來賓提問」素材,避免 LLM 憑空編出弱智提問;單人版可作自問自答的轉折 |
| `必須保留的限定語` | 文章的謹慎措辭在口語化中最容易被潤掉,變成過度肯定的斷言;獨立成欄等於強制不可省略 |
| `陳述強度` | 對應固定口語模板,防止三種陳述被壓平成同一種語氣 |
| `視覺依賴` | 提示渲染 Agent 需將表格改寫為口語敘述;同時保留原始出處供人工核對 |
| `來源段落` / `來源原文摘錄` | single source of truth 的執行基礎;把「這句話對嗎」轉為「這句話能對應回哪一段」 |
| `重要度` + `預估秒數` | 長度控制得以用純程式邏輯完成,不必靠 LLM 猜 |
| `銜接前一個beat` | 避免逐字稿變成獨立段落硬接;必須在裁切後動態填入,否則被砍的 beat 會留下懸空轉場 |

### hook beat(特殊結構)

```
{
  id: "b00",
  type: "hook",
  重要度: "must",
  預估秒數: 15,                // 硬上限
  鉤子類型: "反直覺結果",       // 反直覺結果 / 論文的破綻 / 具體痛點 / 數字衝擊
  內容: "...",
  來源beat: "b07",             // 該 beat 自動升級為 must,不可裁切
  不可劇透: true
}
```

### 揭露 beat

```

  ],
```

## 附錄 B:開場音樂 prompt 三方向

AI 音樂生成工具主要靠「風格詞 + 樂器 + 情緒 + 用途」,不宜寫成長篇散文。

### 方向 A:好奇心驅動

```
Intro theme for a technology podcast, 8 seconds.
Curious and playful electronic, warm analog synth arpeggio,
light marimba, subtle glitch textures, gentle forward momentum.
Intelligent but not cold. Ends on a clean resolved note.
No vocals, no drums buildup, no epic cinematic swell.
```

**設計邏輯**:表達「好奇」而非「權威」。節目的內容特色是拆解、提問、指出缺口——那是探究的姿態,不是宣告的姿態。arpeggio(琶音,音符逐一接續出現)在聽感上有「逐步展開」的意味,與拆解技術的動作相符。

### 方向 B:溫暖易近

```
Podcast intro, 8 seconds. Warm lo-fi electronic with acoustic
guitar plucks, soft Rhodes piano, relaxed but bright.
Approachable, friendly, slightly nerdy. Clean ending.
No vocals.
```

**適用時機**:若「讓非本科聽眾也覺得有趣」的目標權重更高。lo-fi 的親和力高於純電子。

### 方向 C:海洋意象

```
Podcast intro, 8 seconds. Ambient electronic with a sense of
depth and space, soft synth pads, single clear bell motif,
subtle water-like texture. Contemplative yet curious.
No vocals, no cinematic drama.
```

**設計邏輯**:呼應節目名稱中的 Ocean,「深度」雙關內容特性。品牌識別度最高,但風險是可能過慢過柔,開場缺乏推進感。

## 附錄 C:TTS 測試集

完整測試集見 `docs/TTS-TEST-SUITE.md`,含 18 句測試句、評分表與判讀原則。

### 五組結構

| 組別 | 測什麼 | 補救可能性 |
|---|---|---|
| A | 英文專有名詞 | 可用發音詞典修正 |
| B | 縮寫與大小寫混合 | 可用發音詞典修正 |
| C | **中英交界斷句** | **無法補救,不過關即淘汰** |
| D | 數字、百分比、單位 | 部分引擎可設定讀法 |
| E | 長句與語調維持 | 無法後製修正,選型硬指標 |

### 兩個設計要點

**分組而非混測**:不同組的失敗有不同的補救成本,混在一起算總分會誤導判讀。

**D5 是刻意放置的送分題**(純中文數字,任何引擎都應唸對)。若某引擎連 D5 都出錯,代表中文基礎能力不足,可直接淘汰,不必續測。任何評測都值得放一兩題送分題作為基準線。
